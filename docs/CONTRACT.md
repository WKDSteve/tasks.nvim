# The machine contract `tasks-export/1`

What an app, an agent or a pipeline reads from the vault: a handful of JSON documents with a fixed shape, each with a
JSON Schema. The Markdown files stay the single source of truth; the documents are built from what the engine already
knows (`scan`, `plan`, `next_pick`, `estimate`), never from a second reading of the files. Reading is the larger part;
changes go through one door, `ops`, which asks the engine to write ([Writing](#writing-tasks-ops1)).

- [Writing](#writing-tasks-ops1) -- `ops`: `set`, `new`, `reorder`, `done`, `move_area`, `plan_new`, `plan_set`, `plan_close`, `project_new`, `project_set`, `project_close`, `tick_step`, `add_steps`, `answer`, `append_note`, `reopen`, `set_body`, `set_section`, `view_save`, `view_delete`, `attach`, `meeting_new`, `meeting_set`, `meeting_close`, `meeting_capture`, `meeting_attend`, `meeting_followups`, `board_save` (series of meetings), conflicts, `done_preview`, dry runs

## Asking

Every document is one JSON object on one line (the canonical form, below). From a shell:

```sh
export TASKS_VAULT=~/vault
nvim --headless -u NONE -l scripts/tasks.lua call hello
nvim --headless -u NONE -l scripts/tasks.lua call snapshot
nvim --headless -u NONE -l scripts/tasks.lua call list --params='{"area":"my-project","status":["doing","open"],"limit":20}'
nvim --headless -u NONE -l scripts/tasks.lua call task --params='{"id":"my-project/fix-the-thing"}' --pretty
nvim --headless -u NONE -l scripts/tasks.lua --capabilities          # the same as `call hello`
```

`--params=-` reads the JSON from stdin instead (no limit of the command line, nothing for the shell to interpret).

| Method | Parameters | Answer (`kind`) |
|---|---|---|
| `hello` | none | `tasks.hello`: the handshake, reads no task |
| `snapshot` | none | `tasks.snapshot`: counts, areas, the plan head, the plans, the projects and every open task with its readiness |
| `list` | `area`, `status` (list), `project` (list of project ids: the open tasks of those projects, in one of their plans or their own; an empty list narrows nothing), `waits_for` (list of keys; `none`: parked without a reason), `sort` (`default`, `prio-effort`, `severity`, `frecency`, `roi`, `due`, `created-desc`, `created-asc`, `updated-desc`, `updated-asc`, `remind`, `title`), `limit` (1..100), `offset` | `tasks.list`: a page of open tasks in plan order, or in the order of `sort` (the orders of `tasks list --sort`; a tie ends by name; `frecency` reads the usage file of the editor on the machine of the engine and is the default order where there is none; an unknown word is `invalid_argument`) |
| `task` | `id` (`<area>/<slug>`), `finished`? (boolean, capability `task_finished`) | `tasks.task`: one task with its body and steps; with `finished: true` the finished task of that id in its area's `Backlog/` (the first file `find_done` names, FEATURES before TASKS), with `commits` / `done_in`, marked `finished: true`, without `readiness` and `rounds` (an open task of that id is `not_found` then); for a routine (`repeat`, capability `rounds`) also `rounds`: its finished rounds, newest first, at most 100 (`rounds_truncated` when there are more), each `{ id, done, due, status, done_in, commits }` (`done` is the date in the file name below `Backlog/`; fields without a value are absent). A round is a finished task of the same area that carries `repeat` and whose slug without the `-YYYY-MM-DD` of a later round is the routine's. The rounds lie outside the `rev`, as in `finished` |
| `agent_answer` | `kind` (`review-done` or `prepare-decision`), `output` (the `output` of ai-desktop's `GET /jobs/<id>`), `id` (`<area>/<slug>`) | `tasks.agent_answer` (capability `agent_answer`): the answer of an agent's job taken apart for the task by the rules of `:Tasks agent`: the last block of its kind (`<!-- review:begin -->` / `<!-- decision:begin -->`), checked (its heading, no second section of the task's level, no control character, at most 32 KiB; a decision's questions must read as questions of the engine). `sections` (`{ heading, text }`, in the order to write them with `set_section` after a yes), for a review `follow_up` (`{ title, summary? }`, created only after a yes of its own), for a decision `questions_added` (the open questions only when the task, which must wait for a decision, has none of its own). Nothing is written; a broken answer is `invalid_argument` with its reason |
| `bodies` | `ids` (list, up to 1000) or `offset`, `limit` (1..1000) | `tasks.bodies`: `{ id, etag, body, body_truncated }` of the open tasks in plan order, for a reader that searches the text; a page ends early at 2 MiB of text (`next_offset`); the `rev` is that of the snapshot of the same state |
| `estimate` | `ids` (list, up to 1000), `assume` (list of `{ id, effort?, value? }`, up to 1000) | `tasks.estimate`: the figures of an estimate for the tasks named (default: all open tasks) - `tasks`, `days` and its `range` (every size at its low and at its high end), `value`, `n_with_effort`, `n_without_effort`, `n_with_value`, `n_without_value`, `roi`, `quick_wins`, `unestimated` - as they would be with the efforts and values of `assume` (nothing is written; an id outside `ids`, an entry with neither effort nor value, an effort the engine would not write (`XS`..`XL`, or `<n>d` up to 3650 days: a larger number is no effort anywhere, in a file or through the write door) and a value outside 1..5 are `invalid_argument`); `assumed` says how many tasks were taken so. The tasks are in the order of the snapshot, so `unestimated` and `quick_wins` read as there. The figures are those of the snapshot: a client that shows the sum of a draft never reckons it itself |
| `groupings` | none | `tasks.groupings`: the fields the open tasks can be grouped by, in the order `status`, `prio`, `actor`, `kind`, `effort`, `value`, `tags`, `plan`, `phase`, `project`, `area`, `state`, `cross`. Per field `field`, `values` (strings; `value_type` says `number` for `prio` and `value`, so a reader that writes one turns the word back into a number), `truncated` (the values that come from the vault - `tags`, `plan`, `phase`, `project` - are the ones the open tasks name, once each and sorted, at most 200), `writable`, and `mode` for how it is written: `set` (a field of the file: one `set` with `if_match`), `tags` (the list of tags: leaving one tag and taking another is one `set` of the whole list; `multi: true` says a task stands in every group of its tags) or `move_area` (the area: `move_area_preview`, then `move_area`). `project` is derived and has no `mode` either (a task stands in the project of its plan, or in its own; values are the project ids the open tasks stand in, at most 200); `state` is derived and has no `mode`; so is `cross` (after `state`): `several` for a task that `tasks.links` names among the tasks that touch two or more areas (its `tasks`), `one` for every other - a reader takes the value of a task from the `links` of the same `rev`. `status` lists the open statuses: an open task is never in a `done` group. The same `rev` as the `snapshot` of the same vault, so a reader draws groups from the tasks of that very state. A reader that shows groups and lets a task be dragged names no field and no value itself |
| `views` | none | `tasks.views`: the saved views, sorted by `id` (`<area>/<slug>`): each with `title`, `display` (`columns`, `list` or `matrix`), `group_by` (a field of `groupings`) and for a matrix `group_by2`, `collapsed` (the groups that are folded), `select` (`areas`, `statuses`, `actors`, `kinds`, `tags`, `plans`, `projects` as lists - empty narrows nothing - and `query`), the `etag` of the file and its dates. A file in `<area>/ROADMAP/views/` that cannot be read as a view is no view but a line of `problems` (`id`, `file`, `message`, without a path of the machine). The `rev` is that of the views, not of the tasks. A folder of views that leads out of the vault (a symbolic link or a junction) is a problem named `<area>/views`, a view file that is a link a problem of its own: neither is read, and `view_save` and `view_delete` refuse them with `forbidden`. A view holds no task and no rule: it is a way to look at the tasks, kept in the vault so it is the same on every machine |
| `lists` | none | `tasks.lists`: the named lists of the engine, read only - the built-in ones, the ones saved with the editor (`tasks lists save`) and the ones of the configuration (`setup({ lists })`), by name, the later source winning. Per list `name`, `source` (`builtin`, `saved`, `config`), `desc` when it has one, `summary` (the line the engine shows) and `options`: the option words of the command line as strings (`effort: "<=S"`, `sheet: "none"`, `claimed: "foreign"`), a switch as `true`. The built-in lists `abnahme-inbox`, `abnahme-manual` and `abnahme-by-hand` are the three groups of the acceptance (a test sheet waiting for judgement, a sheet by hand, a live check `needs-live-test` without a sheet). A definition the engine rejects is not a list but a line in `notes` (with a list another source shadows and a state file that cannot be read - told without its path). Running a list is the reader's job: its words mean what they mean on the command line |
| `order` | `area`, `status` (list), `project` and `waits_for` (as in `list`), `sort` (as in `list`) | `tasks.order`: the ids of the open tasks in the order of `sort` (the plan's order without it), all in one document (`sort`, `total`, `ids`, `incomplete`) - for a reader that lays the tasks it holds along an order and would otherwise page through `list` for it, one read of the vault per page of 100. The ids are those the pages of `list` with the same parameters join up to |
| `plan_compare` | `ids` (open plan ids; default: every open plan) | `tasks.plan_compare` (capability `plan_compare`): the open plans side by side, one row each in the order of the vault - `tasks` (open, finished, the open ones by readiness state), `progress` (finished of all, two decimals), `effort` (open days with the range of the sizes, finished days, open tasks without an effort), `path` (the critical path of the plan's open tasks alone, in days, and how many on it have no effort), `stages` and `phase_now` (the first stage of `phase_order` that still has an open task), `last_done`, `weekly_done` (members finished in each of the last `weeks` weeks, oldest first, the last ending `today`) and `forecast_weeks` (`low` at the pace of the best of those weeks, `high` at their average; absent when nothing was finished in them or nothing is open), `value` (over the open tasks: `sum`, `avg` of those that carry a value, `without`), `prio` (the best prio among them), `areas` (the plan's own area, then the others it names), and for a plan whose `target` task is open and has a `due`: `target_due`, `due_in_days` (negative when it has passed) and, with a forecast, `forecast_late` (the `high` end of the forecast lies after that day). It counts tasks, not their effort. An id that is no open plan is refused (`invalid_argument`). The finished tasks lie outside `rev`, as in `tasks.finished`; a page that compares plans only sorts and draws the rows |
| `plan_for` | `id` (an open task), `direction` (`needs`, the default, or `unlocks`) | `tasks.planfor`: the tasks `id` needs before it can start (its hard blockers, transitively, across areas: `blocked_by` and the gate of a plan) or, with `unlocks`, the tasks that wait for it - `nodes` (`id`, `title`, `status`, `state`, `stage`, `distance` from the task, `on_critical_path`), the hard `edges` between them (`from` is finished first; `kind` is `blocked_by` or `gate`) and the `cycles` among them (a cycle is named only when all its members are among the nodes); at most 500 nodes (`total` and `truncated` say the rest). The tasks are those of `plan --for`; a client that shows the graph never walks it itself |
| `check` | `area`, `stale` (`refs`) | `tasks.check`: the rule check of the vault (`tasks check`) as `findings` (`code`, `severity` `error` or `warn`, `area`, `id` when there is a task, `file` relative to the vault, `message` - the engine's words, untrusted text) with `errors`, `warnings`, `areas`, `tasks` and `ok`; with `stale: refs` also a `stale-refs` warning for each open task that names a file which changed after the task was updated (counted in `warnings` like the others; `notes` tell what could not be checked, never with a folder of this machine); errors come first, then the findings by file, code, task and wording; at most 1000 findings (`total`, `truncated`). It reads every task file and asks git: a client runs it as a job. Its `rev` is that of the open tasks, as everywhere: a finding about a file that is no open task (the index, the Backlog, a plan file) can change without it. A client that keeps the findings while the person works judges them one by one, not the document as a whole: it takes the `etag` of every task from the `snapshot` of the same `rev` as the ground, and a finding with an `id` holds while that task has the same `etag`, is possibly resolved when it changed, and is dropped when the task is gone; a finding without an `id`, or about a task the snapshot does not list, has no version to go by and stands as of `generated_at` |
| `next` | `n` (0..10), `actor`, `area`, `not_category` (a list of categories; capability `next_not_category`) | `tasks.next`: what to start next, with the reason. A ready task of a category in `not_category` (its `category`, `bug` for `kind: bug`, a tag spelled like a category, as `--category` of `list` counts them) is left out: not offered, not in `cdx`, not counted as ready; `left_out` says how many, absent when none |
| `areas` | none | `tasks.areas`: the areas with their open counts and, when the vault has any, the area groups in force (`area_groups`: `name`, `members`, `open`, `by_status`, `desc`) |
| `find` | `refs` | `tasks.find`: the tasks, open and finished, whose `refs` name one of the refs (at most 50): `matches` of ref, id, area, status, `open`/`done` and `kind` (`task`, or `meeting`: a meeting that names the task id), never a path |
| `intent` | `intent`, `yes`?, `lang`? | `tasks.intent`: take an intent `wkd-intent/1` (capability `intent`): checked as untrusted input, answers `would_create`, `exists`, `shown` or `not_found`, and with `yes` `created` (the one method of this table that can write; the ops door is the other). A refused intent is `invalid_argument` with every problem in the message. See [ENGINE.md](ENGINE.md#taking-an-intent-wkd-intent1) |
| `waits` | `area` | `tasks.waits`: what the parked tasks wait for - per `waits_for` key the number of tasks and their areas, the parked ones without a reason, the total |
| `links` | none | `tasks.links`: where the areas hang together - the links between the open tasks of different areas by pair of areas (`blocked_by`, `after`, a ref that names another area, a plan whose open tasks lie in several areas) and, for every task that touches two or more areas, the areas it touches |
| `finished` | `area`, `plan`, `since`, `until` (days, both included), `limit` (1..100), `offset`, `ci` (a list of `pending`, `green`, `red` and `none`; capability `finished_ci`) | `tasks.finished`: the finished tasks of the Backlogs, newest first, and what all of them add up to; with `ci` only those whose CI state is one of them (`none`: no `ci` written), so `total` of `ci: ["pending", "red"]` is the number of finished tasks whose CI has no verdict yet or is red |
| `history` | `area`, `since`, `until` (days, both included; default: the 90 days up to today), `resolution` (`day`, the default, or `week`) | `tasks.history` (capability `history`): the figures of the overview over time, one point per day or week, oldest first; at most 800 points (more is `invalid_argument`: ask for weeks or fewer days) |
| `meetings` | `since`, `until` (days, both included; default: the 30 days before `today` and the 90 after), `area` (an area or an area group), `status` (list of `planned`, `done`, `cancelled`), `task` (an id: the meetings that name it), `limit` (1..100), `offset` | `tasks.meetings` (capability `meetings`): the meetings whose days touch the window, the earliest first (then by id), one page: `items` (meeting entries, below), `total`, `offset`, `limit`, `next_offset` while there is more, `since` and `until` as used, `undated` (meetings that match but have no valid date: in no window; `check` names them) and `incomplete`. A series is listed as its occurrences in the window, not as itself (capability `meeting_series`): an occurrence with a file in place of its day (also when its `date` was moved), the others computed (`virtual`), at most 500 of one series (the rest named in `incomplete`); the excepted days and those after `repeat_until` have none. The revision is over the meetings of the page |
| `paths` | `area` (an area or an area group; default: all), `include_done` (capability `requires`) | `tasks.paths` (capability `paths`): the open learning paths (with `include_done: true` the finished ones of those areas too, read from the Backlogs, after the open ones) (`<area>/ROADMAP/paths/`), each as a **path entry**: `id`, `area`, `slug`, `title`, `status` (`planning`, `doing`, `parked`, `done`), `areas`, `target`, `project`, `created`, `updated`, `summary`, `has_tree` (a `## Lernpunkte` section), `points` (its learning points, parents included), `progress` (`learned`, `seen`, `dropped`, `open`, `blocked`, `total`: over the leaves; a blocked one counts as open and once more as blocked), `links`, `icon`, `cover`, `folder`, `assets`, `file`, `etag`, `valid`, `problems` (the faults of the file, as text), and with capability `xp`: `xp` (`earned`, `possible`, `open`, `points`, `missing`; only when a point carries XP) and `level` (only when the file has `## Level`: `level` reached, `name`, `badge`, `percent`, `finished`, `next { number, name?, missing_xp?, missing_percent? }`, `open_rewards [{ ref, reward }]`), and with capability `optional_points`: `optional` (`progress`, and `xp` when the tree has XP; only when the tree has optional points: a node marked `{optional}` and its subtree). `progress` and `xp` leave the optional points out, so they count for no level in percent and not for `finished`; a level in XP counts their XP once earned. And with capability `requires`: `requires` (`{ id, gate, kind, met }` in the file's order: `kind` `path`, `project` or `unknown`, `met` the requirement is finished; only when the file names some), `requires_gate` (the file's gate, `soft` or `hard`) and `waiting_on` (`{ id, via? }`: the open HARD requirements, for a path also those of its project with `via` the project; empty: it may be finished; present when it names or inherits a requirement). An open soft requirement is a hint only: it is in `requires` (`met: false`), never in `waiting_on`; a path that waits has its `level` read `finished: false` without the reward of the whole path. With capability `requires` every path entry carries `stage` (`done`, `parked`, `waiting`, `doing`: `status: doing` or a point learned or seen, else `idle`), and the document `requires_cycles` (the circles of requirements among the open paths and projects, each from its smallest id) and, with `include_done`, `done_projects` (`{ id, area, title }`: the finished projects a requirement names); both only when a path or project names a requirement. With capability `path_hours`: `hours` (`planned_min`, `planned_max`, `done`, `open_min`, `open_max`; only when a point carries `{h=…}` or `{done_h=…}`): planned are the hours of the outermost points that carry `{h=N}` or `{h=N-M}` (an inner point is part of its outer one), done those of `{done_h=N}` (outermost too), open the planned hours of the points not closed less what was done on each, never below 0; a point whose leaves are all dropped plans nothing, optional points count for nothing, sums keep two decimal places. No tree; `incomplete` names areas that could not be read. The revision is over the path files and the `xp:` of the tasks their promoted points name, and the state of the requirements of the paths that name some |
| `path` | `id` | `tasks.path` (capability `path`): one path: `path` (the entry), `body` (cut at 256 KiB with `body_truncated`), `progress`, `tree_problems` (`{ code, line, key?, message }`, the `path-...` codes of `check`) and `nodes`, the tree as a **flat list in document order**: `{ index, line, depth, parent?, children, mark, state?, derived, closed, label, key?, reason?, promoted?, link?, image?, note?, progress }`. `parent` is the `index` of the parent (absent for a root); a parent has no mark of its own, its `derived` state is `learned`, `partial` or `open` from its leaves, and it is `closed` when every leaf is (when it has points that are not optional: every one of those; its `progress` counts every leaf below it, optional ones too). With capability `optional_points` a point that is `{optional}` or below one carries `optional: true`. With capability `path_marks` a point carries `machine` (the machines it is for: its own `{machine=a,b}`, else the nearest parent's; absent: every machine) and `safety: true` (it is `{safety}` or below one). `promoted` names the task the point was promoted to, which owns its state. `state` is absent for an unknown mark. `label`, `note` and `body` are untrusted text; an `image` is a file below `assets/` of the path, drawn as an image only. A point is named by its `key`, or by `#<index>` where it has none. An unknown path is `not_found` With capability `path_hours` and when the entry has `hours`: `schedule`, the sessions of `## Zeitplan` (the points with planned hours that are a root or one level below, as `tasks path --schedule` lists them), each `{ index, key?, label, result?, state, closed, total }` (`state` `open`, `partial` or `done`, `result` the text after `Nachweis:`/`Aufgabe:`/`Ergebnis:` of its first such child) with its own hours as above. |
| `learn_evidence` | `competence` (an id: only the paths that serve it), `area`/`areas`, `paths`, `include_done` (the finished paths too: their evidence is the portfolio) | `tasks.learn_evidence` (capability `learn_evidence`): the evidence of all learning paths, the engine's rule: a point whose label starts with `Nachweis:`, `Aufgabe:` or `Ergebnis:` (`Evidence:`, `Result:`; any case, the word and colon first). `{for=t4}` / `{for=p3.5}` on it names the stage of the competence scale it proves (`t` theory, `p` practice, 0..8 in halves; anything else is the tree problem `path-bad-for`). Each item `{ path, area, title, path_done?, competence?, index, key?, label, stage_index, stage_label, state, link?, for? { axis, level } }` (`competence` the ids the path serves, `state` the one shown: `learned` is evidence given), open paths by id, then the finished ones, each in document order. The revision is over the path files (and whether they are finished) |
| `learn_next` | `area` (an area or an area group; default: all), `paths` (ids of open paths; default: all), `machine` (`private`, `workstation`, `wsl`; default: every machine), `n` (1..20, default 3) | `tasks.learn_next` (capability `learn_next`): what to learn next, the engine's rule (the page computes none). The running paths are those of stage `doing` (`status: doing` or a point learned or seen) and the `idle` ones whose project has `status: doing`; never a parked or waiting one. For each the first `n` points in document order that may be learned now: a leaf, open (an unknown mark reads as open; blocked does not), not `{optional}` nor below an optional node, and, with `machine`, one that may be practised there (`{machine=…}` as in `tasks path --machine`; the private machine has WSL). `items` `{ path, area, title, icon?, project?, stage, points }`, only paths with such a point: `doing` before `idle`, then the most recently `updated`, then by id. A point is a **learn point** `{ index, key?, label, stage_index, stage_label, link?, promoted?, h_min?, h_max?, xp?, safety?, machine? }`: the stage is the root it stands below (its own for a root), `h_min`/`h_max` its planned hours (`{h=N}`, `{h=N-M}`), `safety` the `{safety}` above it (closing it needs `ack`). `machine` echoes the request; `incomplete` names areas that could not be read. The revision is over the path files, the `xp:` of the tasks their promoted points name and the status of their projects |
| `learn_notes` | `query` (a part of the label, the note or the link, without case; at most 200 bytes), `kind` (`note`, `link`, `image`), `area`/`areas` (areas or area groups; default: all), `paths` (ids), `include_done` (the finished paths of those areas too), `limit` (1..500, default 200) | `tasks.learn_notes` (capability `learn_notes`): the points of all learning paths that carry a note (the `> ` lines below them), a link or an image (every point, a stage and an optional one too), each `{ path, area, title, path_done?, index, key?, label, stage_index, stage_label, state, note?, link?, image? }` (`state` the one shown, `PathNode.derived`; `path_done` a finished path), open paths by id, then the finished ones, each in document order. `total` counts every hit, `truncated` says `limit` cut them. Texts are untrusted (Markdown); an image is a file below `assets/` of the path, drawn as an image only. The revision is over the path files (and whether they are finished) |

The exit code of `tasks call` is `0` for an answer, `2` for `invalid_argument`, `1` for any other error. An error is a
`tasks.error` document on stdout like any answer, so a reader parses one stream. `--pretty` indents the same document.

The command line also has a few forms of the same documents: `tasks list --format=json [--limit=N] [--offset=N]` (the
filters of the text form, the plan's order, or that of `--sort`), `tasks next --format=json`,
`tasks areas --format=json|tsv`, `tasks waits --format=json`, `tasks show <id> [--format=json|text]`, `tasks plans [area]`, `tasks list --done`
(the finished tasks of the Backlogs) and `tasks history [area] --format=json` (the `tasks.history` document).

From Lua, `require("tasks_nvim.api").call(method, request, { root = ..., indent = ... })` is the one door. It answers
with the text of the document and an error code (`nil` for an answer) and **never throws**: an unreadable vault, a
bad request and a bug of the engine are all a `tasks.error`.

A request is a JSON object, `{ "schema": 1, "params": { ... } }`. Both fields may be left out. A field or a parameter the
method does not know is `invalid_argument`: a request that is silently half-understood is worse than one that is refused.
A request is at most 256 KiB.

the entries of `done`, `node_set` and `path_close` carry `routines_started` (`{ id, due, after }`: the routines that waited for what the operation finished and got their first `due`, which is that day plus the first interval), whose ids are in `changed_ids`), plus the capability `rounds` (`tasks.task` of a routine carries `rounds`, its finished rounds), plus the capability `projects` (the snapshot carries `projects`, plans carry `project` and `phase`, task entries `project`, `donepreview` `closes_project`, a finish answers `projects_closed`), plus the capability `icon` (task entries, the plans and projects of the snapshot and meeting entries carry `icon` `{ kind, value }` and `cover`, only when the file has them: `kind` `emoji` (one emoji, one grapheme cluster), `asset` (a file below `assets/` of the item's folder, png, jpg, jpeg, webp or svg) or `word` (one of `enums.icon_word`, the old meeting icons); `cover` is a picture below `assets/`. A client draws an asset, an SVG too, only as an image, never as inline markup. The engine hands on the fields of the item; whether a task falls back to the icon of its path or its category is the client's. `new` takes both in `fields`, `set`, `plan_new`, `plan_set`, `project_new`, `project_set`, `meeting_new` and `meeting_set` take them, `null` removes them; a value that is none of the forms is `invalid_argument`. A meeting's `icon` was a word as text before and is `{ kind, value }` now; its `image` is the old name of `cover` and carries the same value), plus the capability `outcome` (how a finished task ended beside `status: done`: task entries and the items of `tasks.finished` carry `outcome` (`learned`, `seen`, `not-applicable`; absent: done as meant, or not finished yet), `outcome_reason` and `point` (`<container id>#<key>`: the learning point the task was promoted from), only when the file has them; an open task may carry them as a note in advance. `done_preview` takes `outcome` and `outcome_reason` and answers them with the Backlog row that names them; the operation `done` takes them, refuses `seen` and `not-applicable` without a reason (unless the task carries one) and an unknown word with `invalid_argument`, and answers `point { container, key, state, changed }` when the task came from a learning point (the container is in `changed_ids` when its file was written). `groupings` has the field `outcome` (`set`)), plus the capability `xp` (XP, levels and rewards of the learning paths: task entries and the items of `tasks.finished` carry `xp`, `new` takes it in `fields` and `set` in its patch; `tasks.paths` and `tasks.path` carry the XP and the levels described there, a path without XP and levels reads as before; learned counts in full, seen half (rounded down), dropped leaves sum and maximum; the level is the run of levels reached from level 1 on; `node_set` takes `xp` / `xp_clear`), plus the capability `path_reward` (the operation of the same name), plus the capability `optional_points` (optional subtrees of a learning path: a node marked `{optional}`, mostly the group of books, and its subtree count for nothing that says how far the path is; `tasks.paths` and `tasks.path` carry them apart as `optional`, the nodes of `tasks.path` as `optional: true`), plus the capability `path_marks` (`{machine=...}` and `{safety}` on a learning point: the nodes of `tasks.path` carry `machine` and `safety`, `node_set` takes `ack`), plus the capability `path_levels` (the operation of the same name: the levels of a path written as a whole), plus the capability `ci` (the CI state of a task's commits beside `commits`: task entries and the items of `tasks.finished` carry `ci` (`pending`, `green`, `red`; absent: not known), only when the file has it; the operation `done` takes `ci` (an unknown word is `invalid_argument`) and `set` takes it in its patch, on a finished task too: `ci` is bookkeeping like `remind`, so `set` finds the task in `Backlog/` when no open task has the id and changes nothing else there), plus the capability `requires` (learning paths and projects that build on each other: `requires: [id, ...]` and `requires_gate: soft|hard` in the file of a path or project, never a plan (`plan-requires`). A requirement is met once that path or project is finished (closed into a Backlog). The soft gate only says so (the item keeps its stage); the hard gate keeps the path or project from being finished, and a hard requirement of a project holds for each of its paths too, (`path_close`, `project_close` and a finish by `done` that would close the project) and the line of the whole path in `## Level` open. Work may start at any time. `tasks.paths`, `tasks.path` and the projects of the snapshot carry the fields named there; `path_new` and `project_new` take `requires` and `requires_gate`, `path_set` and `project_set` take them in the patch (a requirement is written as its id; an empty list removes the key). An id that is no learning path or project of the vault (`requires-unknown`) and a circle through the file (`requires-cycle`) are refused with `invalid_argument` and `details.problems`; `check` reports both), plus `marker` (optional, additive; capability `vault_marker`): `present` (the vault has a `tasks-vault.json`), `layout_version` (of a valid file) and `problem` (why a file is refused; no path). A refused file fails every other call with `invalid_argument` and the message `tasks-vault.json: <reason>`; `hello` is the one that still answers. See [ENGINE.md](ENGINE.md#the-marker-file-tasks-vaultjson). Plus `enums.scaffold`: the fixed acceptance lines by kind, category and scope (`kind`, `category`, `scope`: word to rows `{ id, de, en }`; `implied`: scopes whose rows a kind and category also get). A client joins the rows of what applies, each `id` once, in the order kind, category, scope (the order of the lists).

A **task entry** (`tasks[]`, `items[]`, `task`) has: `id`, `area`, `slug`, `title`, `status`, `kind`, `prio`, `order`,
`effort`, `effort_days`, `value`, `roi`, `actor`, `actor_written`, `severity`, `waits_for` (what a parked task waits for from outside: one key, a lower-case word of a-z, 0-9 and `-`, at most 40 characters; optional, only when the file names a valid one), `created`, `updated`, `plan`, `phase`,
`done_in`, `commits` (every commit made for the task, `repo@sha` each; only when the task lists any), `ci` (capability `ci`: the CI state of those commits, `pending`, `green` or `red`; only when the file has it), `remind` (a date: look at the task again then; whether it is due is for the reader to say, the entry does not change with the day), `remind_at` (the local time of day, `HH:MM`, the reminder of that day is sent; only beside `remind`), `remind_to` (the
e-mail addresses the reminder goes to, only valid ones, only beside `remind`), `due` (a date: the deadline, optional; not the reminder) and `start` (a date: the earliest day to begin, optional, never after `due`), `tags`, `category`, `scope` (what the task touches, `hello.enums.scope`; only when the task names any), `blocked_by`, `after`, `late_blockers` (the open blockers due after the task begins: `id`, `kind` `blocked_by` or `after`, their `due`, and `against` `start` or `due` - the date of the task they are later than, its `start`, else its `due`; only when there are some, a parked task has none; capability `late_blockers`, the rule of the `blocker-late` hint of `tasks check`), `refs`, `links` (web addresses, `http://` or `https://` only, apart from `refs`; only when the task lists any), `icon` and `cover` (only when the task has them; capability `icon`, see below), `outcome`, `outcome_reason` and `point` (only when the task has them; capability `outcome`, see below), `xp` (the XP of a learning task, only when the file has them; capability `xp`, see below), `summary`, `meetings` (the ids of the meetings that name the task in their `tasks:`, the earliest first, at most 20, `meetings_truncated` beyond; only when there are some; capability `meetings`), `folder`, `file` (`<area>/ROADMAP/tasks/<slug>.md`,
relative to the vault), `valid`, `problems` (`[{ code, msg }]`), `steps` (`total`, `ticked`, `dropped`, only when the
task has a `## Plan` section), `open_questions` (how many questions of its `## Offene Fragen` section are not answered; only when
there is one), `sheets` (the test-sheet block testing.nvim writes into a live-check task, read from its states line:
`state` = the worst sheet, one of `red`, `stale`, `never`, `inbox`, `manual`, `green`, or `unknown`; `total`; `counts` per
state; `reason` only for `unknown`: `no-states-line` (an older testing.nvim), `no-known-state` (a newer one),

with; only when the task has the block), `etag` and, for an open task, `readiness`:

```json
"readiness": { "state": "ready", "stage": 0, "rank": 3, "eff_prio": 1, "leverage": 4, "open_blockers": [] }
```

`state` is `ready`, `decision`, `waiting`, `stuck`, `freed` or `parked` (the one definition of "can be started",
`tasks_nvim.plan`); `inversion`, `in_cycle` and `same_file` appear when they apply. `group` is `<status>|<eff_prio>` (`-` without
a priority): it is the guard of `reorder` and nothing a client takes apart -- the priority of a task is `readiness.eff_prio` (missing
when there is none), which the capability `eff_prio` promises equals the part after the bar. An engine without the capability
is not read as "no priority".

**`tasks.donepreview`** and **`tasks.result`** belong to writing and are described there.

**`tasks.list`** -- `total` (all matches), `offset`, `limit`, `items` (task entries) and `next_offset` while there is
more. Pages are 100 entries at most. **`tasks.task`** -- `task`, `body` (the Markdown after the frontmatter, cut at 256 KiB
with `body_truncated`) and `steps` (`[{ n, text, ticked, dropped }]`) and `questions` (`[{ n, key?, title, text, answered, options: [{ n, text, recommended, chosen }] }]`, empty without the section; see [the questions of a task](#the-questions-of-a-task)). **`tasks.next`** -- `task` (`id`, `title`, `status`,
`prio`, `effort` and the `reason`), `alternatives`, `cdx` (the queue written for the AI), `freed`, `ready` and `open`
(counts for the area and the vault) and, when there is no task, `empty` (`kind`: why; `parked` and, when parked tasks name
what they wait for, `waits_for`: key to number of tasks). **`tasks.areas`** -- `areas`.

**`tasks.waits`** -- what the parked tasks wait for, of the vault or of `area` (an area group too): `keys`
(`[{ key, count, areas }]`, the key with the most tasks first, then by name), `without_reason` (parked without
`waits_for`: set aside by choice), `invalid` (parked with a `waits_for` that is no key, the `invalid-waits-for` finding),
`parked` (all of them: the sum of the three) and `incomplete`. Same `rev` as the snapshot of the same state. The tasks
of a key are `list` with `waits_for: ["<key>"]`. A task entry carries `waits_for` (capability `waits_for`); the `set`
operation takes it in `patch` and `new` in `fields`, and the two keys move together: a reason parks the task, a status
other than `parked` drops the reason (the `inverse` names both), `status` other than `parked` together with a reason is
`invalid_argument`. There is no operation of its own for releasing a key: a client sends one `set` with
`{ "status": "open" }` per task of `list`.

**`tasks.links`** -- `pairs` (`a` sorts before `b`; `count`, `kinds` - how many edges of each kind - and `edges`: `from` the task, `from_area`, `to_area`, `kind` `blocked_by`/`after`/`refs`/`plan` and `to` the other task or the plan, or `ref` as written), the busiest pair first; `tasks` the open tasks that touch two or more areas with `areas`; `edge_count`; `truncated` when the edges of the pairs were cut at 2000 (counts and `tasks` cover all). A ref is a link only when it names a known area as `area@sha` or `area:anchor` (an anchor is one word that starts with a letter); a ref with a path, also behind an area name, says nothing about the repo. A plan links the areas its open tasks lie in, as one edge per pair of areas (the first member, by id, of the lower area stands for it; its `areas` list says who may join, the members who did). When the edges are cut, the waits stay before the refs before the plans, and every pair keeps at least one edge. Finished tasks are not part of it. Same `rev` as the snapshot of the same state.

**`tasks.finished`** -- the finished tasks of `<area>/Backlog/TASKS|FEATURES`, which no other document lists (the snapshot has only those with a reminder). `items` is one page, newest first (the same day by id): `id`, `area`, `slug`, `title`, `plan`, `phase` (as written), `done` (the day in the file name `YYYY-MM-DD_<slug>.md`; absent for a file without one), and when the file says so `kind`, `prio`, `effort`, `effort_days`, `value`, `done_in`, `commits` (`repo@sha` each), plus `tags` and `file`. `total`, `offset`, `limit` and `next_offset` page as in `tasks.list`. `since` and `until` narrow by the `done` day; an undated file is not in a window but is counted in `undated` (of the area asked for, whatever the window or the plan). The area is the one the file is in now (a task moved with `move_area` before it was finished counts for the new one). `stats` covers ALL tasks that match, not the page: `effort_days` (the sum of the written efforts) and `without_effort`, and the rows `by_area`, `by_kind`, `by_prio` (the biggest first), `by_month` (`YYYY-MM`) and `by_week` (`week` is the Monday) (oldest first), each `{ <key>, count, effort_days }`; a row for the tasks that do not carry the field has no key (missing means unknown). Nothing is cached: every call lists the Backlog folders and parses the files through the parse cache (a second look at an unchanged file is a stat), so a client asks for the page it shows and for the window it needs, not for everything on every refresh.

**`tasks.history`** -- the figures of the overview over time (capability `history`), for a curve behind a tile. The engine only knows the vault as it is now, so it writes the figures down when they change: one JSON line per day and area in `<vault>/_Telemetry/history/YYYY-MM.jsonl` (see [ENGINE.md](ENGINE.md#the-series-of-the-figures-_telemetryhistory)). `points` has one entry per day of the window `since`..`until`, oldest first: `day`, `done` (tasks finished on it: the date in the name of the Backlog file) and `created` (tasks, open or finished, whose `created` is that day) come from the files and are there for every day; the level of the day comes from the series: `open`, `by_status` (the open statuses), `by_state` (`ready`, `decision`, `waiting`, `stuck`, `freed`, `parked`: the figures of `plan.summary` of the snapshot, so a tile and its curve mean the same number), `with_effort`, `with_value`, `effort_days` and `value` (the sums of the written efforts and values). A level is the sum over the areas of the last row each of them has up to that day; it is absent before the first row (unknown, never 0), all of its fields or none. `recorded` is true when a row of the areas asked for was written on that day; a level without it is the one carried over (nothing was written down, which is also what an unchanged vault looks like). With `resolution: week` a point is a week named by its Monday: the level of its last day in the window, the sums of `done` and `created`, `recorded` when one of its days is. `area` (an area or an area group) narrows all of it and is echoed. `first` and `last` are the first and last day that has a row of the areas asked for (absent without a series): a reader that gets only points without a level tells "no series yet" from "the window is before it". `incomplete` names what was skipped: a line of the series that is no row (`<file>:<line>: <why>`), a folder that could not be read; the rest is still the answer. The series lies outside the revision, as in `tasks.finished`, and every call parses the Backlog files through the parse cache as `finished` does.

**`tasks.meetings`** and **`tasks.meeting`** -- the meeting files (`<area>/MEETINGS/<slug>.md`, see [ENGINE.md](ENGINE.md#meetings-meetings)). A **meeting entry** has `id`, `area`, `slug`, `title`, `status` (`planned`, `done`, `cancelled`; absent for a file with no valid one), `date`, `time` (the beginning; absent: all day), `end` (as written), `duration_min`, `all_day` (beside a valid date), `starts_at` and `ends_at` (`YYYY-MM-DDTHH:MM`, or the day of an all-day meeting: its first and last day), `tz` (an IANA zone the times are written in; the engine does not convert), `location`, `online` and `online_service` (`teams`, `zoom`, `meet`, `webex`, `jitsi`, `link`), `tasks`, `notify` (`{ spec, before_min? }` or `{ spec, days_before, at }`), `notify_set` (`true` only when the file names `notify`: an empty `notify` is then "no notice"; without it the reader applies its own default), `notify_to`, `cover` (below the meeting folder; read from `image:` as well, its old name), `image` (the same value, for the readers of before), `icon` (`{ kind, value }`, capability `icon`), `tags`, `recording`, `created`, `updated`, `summary`, the counts `participants` (`total`, `present`), `agenda` and `followups` (`total`, `ticked`), `has_result`, `has_decisions`, `has_protocol`, `folder`, `assets` (the files of the folder, as for a plan), `file`, `etag`, `valid` and `problems`. With the capability `meeting_series`: a series carries `repeat` (normalised: `1w`, `2w`, `1m`; the words `daily`, `weekly`, `monthly`, `yearly` are read as `1d`, `1w`, `1m`, `1y`), `repeat_until` and `except` (the days without an occurrence); an occurrence carries `series` (the id of the series) and `occurrence` (its day in the series, the day in its slug `<slug of the series>-<day>`; `date` differs when it was moved), and `virtual: true` while it has no file: then `etag` is the version of the series file and `file` the file it gets. Nothing in it changes with the day: whether a meeting is past, and which notification is due, is for the reader to say from `starts_at`, `ends_at` and `tz`. The snapshot carries no list of meetings; the task entries carry `meetings`, and a changed meeting file changes the snapshot's `rev`.

## Writing: `tasks-ops/1`

Changes go through one door, `ops`: a list of operations answered with one `tasks.result`. The engine stays the only
writer and the only implementation of the rules; a front end never touches a file.

```sh
echo '{"client_op_id":"c-1","ops":[{"op":"set","id":"my-project/fix-the-thing","patch":{"status":"doing"},"if_match":"sha256:3f6c9a1e0b7d4c22"}]}' \
  | nvim --headless -u NONE -l scripts/tasks.lua call ops --params=-
```

(`--params=-` reads the request from stdin, so there is no limit of the command line and the shell never sees it. For
`ops` the JSON is the whole request; for the read methods it is their `params`.)

A request is `{ "schema": 1, "client_op_id": "c-81f2", "dry_run": false, "ops": [ ... ] }`. `client_op_id` (1 to 64
characters of letters, digits and `. _ : -`) is echoed in the answer, for a client that must not repeat itself;
`dry_run` checks everything and writes nothing. A task an earlier `new` of the same request would create counts, as
in the real run, for the `after` and `blocked_by` relations of later operations (as an id or a bare
`[[slug]]`; not `after-dangling`, its relations are edges of the `blocked-by-cycle` check) and its slug is taken (a
repeated title gets `-2`). A plan or project an earlier `plan_new` or `project_new` of the same request would create
counts, too: a later `new` or `set` may name it in `plan`, `project` and `phase` (its `phases` are the stages), and a
later `plan_new` may name such a project. An operation on such a task (`set`, `done`, `tick_step`, `answer`, `append_note`,
`add_steps`, `set_body`, `reopen`, `attach`, `reorder`, `move_area`) works on the file that `new` would write, and a
`set` or a text change (`tick_step`, `answer`, `append_note`, `add_steps`, `set_body`) carries that file on, so a later
operation of the request finds the task as the real run leaves it and names the same `etag_before`. (`done`, `reopen`
and `move_area` do not carry on, on purpose: the operation after one of them still sees the file before it. A draft
knows one state, open; a finished or moved state would change what every later operation answers, and no client sends
`set` and then `done` of the same task in one dry run that needs the second answer.) A `done` after a
change of the same task therefore takes the confirm token of its own preview. At most 100 operations.
`attach_dirs` (optional, at most 8 absolute paths) names the folders `attach` with `from: latest` takes the newest
image from, instead of `attach.screenshot_dirs` and the folders of the system;
given and empty, `latest` is refused (`invalid_argument`) and only the clipboard is read. It is the field of a caller
that runs the engine for a page (the hub, from its own settings): a page never names a folder. `null` counts as not
given. With `attach_dirs` a failed `latest` names no folder and no file (`no new image in the screenshot folders of
the hub`).
`upload_dir` (optional, an absolute path) names the folder `attach` with `from: upload` takes its file from. It is a
field of the same caller: a page never names a folder.

**Meetings and the task operations.** `tick_step` and `add_steps` take a meeting id and work on its `## Agenda`, or on
`## Folgeaufgaben` with `section: "followups"` (a task takes no `section`); `append_note` writes a line of the minutes,
`set_section` and `set_body` the meeting's body, `attach` its assets (new kinds `audio` and `board`, for tasks too). A
`move_area` of a task rewrites `tasks:` and the follow-up arrows of the meetings that name it (reference and `rewritten`
kind `meeting`) and is blocked by a meeting of the same slug in the target area. A `done` of a follow-up task ticks its
line in the meeting its `refs` name. `find` names, beside the tasks, the meetings that name a task id it is asked for
(in `tasks:` or behind a follow-up); every match carries `kind` (`task`, `meeting`), a meeting is `open` while planned.
The CLI has the same: `tasks meeting new|set|close|followups|attend|show|parse`, `tasks meetings`.

**Series** (capability `meeting_series`). `meeting_new` and `meeting_set` take `repeat`, `repeat_until` and `except` (a
list of days) in `fields` / `patch`. Every meeting operation (`meeting_set`, `meeting_close`, `meeting_capture`,
`meeting_attend`, `meeting_followups`, `board_save`, and `tick_step`, `add_steps`, `append_note`, `set_section`,
`set_body`, `attach` on a meeting) takes the id of an occurrence without a file: the first change makes its file
`<slug of the series>-<day>.md` with `series:` (the series as template, without `repeat`, `repeat_until`, `except`), in
the same write; the entry says `created: true`. A change that changes nothing makes no file (`unchanged`); a dry run
makes none (`would_change`, `created: true`). `if_match` is the version of the series (the `etag` of the virtual
entry); a file made in between is `conflict`. An `inverse` undoes the change, not the file. `repeat` beside `series` is
`invalid_argument`.

**The shape is checked first, for the whole request**: an unknown operation or field, a wrong type, an empty or too long
list is `invalid_argument` (`payload_too_large` for more than 100 operations) and nothing runs. After that every
operation runs on its own, in order, and **one that fails does not stop the others**. This is not all-or-nothing, and
the answer never says "ok" for a part: `ok` of the document is true only when every operation was.

The answer, `tasks.result`, has one entry per operation:

| Field | |
|---|---|
| `n`, `op`, `id` | the position, the operation and the task it is about (for `new`: the id it got) |
| `ok`, `outcome` | `changed`, `unchanged`, `created`, `done`; a dry run says `would_change`, `would_create`, `would_done`, `would_move` (or `blocked`: the move cannot be made); `moved`; `failed` |
| `etag_before`, `etag_after` | the version of the file before and after (a dry run: only before) |
| `inverse` | the operation that undoes it: send it as a new operation, its `if_match` is the version the change left. A key a `set` added is `null` in the inverse patch. `done`, `new`, `append_note` and `reopen` have none in this version (`set_body` and `add_steps` have one unless the old text is too long; `view_save` has one unless the file was no view before) |
| `restore` | a `reorder` only: one `set` for every file it wrote that gives the file its old `order` back (a key the move added is `null`), each with the version the move left in `if_match`. Send them all to take a move back **exactly**: `inverse` only puts the task back in its place, a task that had no `order` would keep one and the neighbours the move numbered stay numbered |
| `changed_ids` | the ids whose files this wrote |
| `index` | what happened to the generated overview of the area: `written`, `unchanged`, `removed` or `error`. It is written **once** for the whole request, however many tasks of the area changed |
| `error` | for a failed operation: `code`, `message`, `retryable`, `details` (see below) |
| `file`, `group`, `renumbered`, `writes`, `to`, `steps_ticked`, `plans_closed`, `projects_closed`, `notes`, `move`, `asset`, `link`, `without_result`, `items`, `preview`, `etag`, `created` | what is particular to the operation |

**Conflicts.** `if_match` and `expect` are checked against the text read **under the file lock**, so two writers cannot
both win: the second gets `conflict` with `details`: `id`, `expected` and `actual` (the version it found) and, for
`expect`, the `key`. Another key of the same file that changed meanwhile is kept, never overwritten. A change of the
relations (`blocked_by`, `after`, `plan`, `phase`) is judged first with the codes of `check` (`blocked-by-self`,
`blocked-by-dangling`, `blocked-by-cycle` with the members named, `after-self`, `after-dangling`, `plan-unknown`,
`plan-phase`): an `invalid_argument` whose `details.problems` lists them. A `reorder` that is not what the caller saw (a
neighbour of another group, neighbours that are no longer next to each other, another `group`) is a `conflict` too: the
list moved on, ask again. A `reorder` is not all-or-nothing: what was written stays, and `details.written` says how far
it got.

**A phase that is no kebab-case word** (`phase` of `new`, `set`, `plan_new`, `plan_set`; an entry of `phases` of
`plan_new` and `project_new`, of `phase_order` of `plan_set` and `project_set`) is `invalid_argument` with the same
message everywhere, `phase '<word>': <what is wrong> (only a-z, 0-9 and single hyphens); try '<suggestion>'`, and
`details`: `field` (`phase`), `value` (the word as given), `char` (the first character that is not allowed; `-` when
the hyphens are wrong; absent for an empty word) and `suggestion` (umlauts and `ß` written out, `ü` -> `ue`, lower
case, every other character a single hyphen; absent when nothing usable is left). Only the first wrong word is named. A
front end may offer `suggestion` in place of the word. A `slug` that is no kebab-case word (`new`, `plan_new`,
`project_new`, `view_save`) is refused the same way, with `slug` as the label and `field`.

**Milestones are reached by the writes that finish their members** (capability `milestones`). After `done`, `reopen`, `plan_close`, `project_close`, `path_close`, `meeting_close`, `meeting_set`, `milestone_new` and `milestone_set` the engine looks at every milestone of the vault: one of `close: auto` (not parked) whose members are all done gets `status: done`, `reached: <today>` and a line in `## Verlauf`; a reached one with a member open again goes back to `doing` (its `reached` stays, a line says which member). The entry of that operation names them in `milestones_reached` and `milestones_reopened` (only when there are any) and adds them to `changed_ids`. A member is done when it is finished: a task, plan, project or path in the Backlog, a meeting `done` or `cancelled`. A member that exists nowhere never counts as done, and a missing one does not open a reached milestone again (that is `check`'s `milestone-include-unknown`).

### The questions of a task

A task that waits for a decision may carry a section `## Offene Fragen` (`## Open questions` in a task written in English):
the questions with the options a person can choose, so that a front end can offer them and write the answer.

```
## Offene Fragen

### Which format? [q1]
Optional text under the question.
- [ ] Section in the body (empfohlen)
- [ ] List in the frontmatter
```

- A question is a `###` heading, ending in its key `[qN]`; its options are the checkbox lines below it, up to the next question. Code fences and
  other sections are not the questions.
- The option that ends in `(empfohlen)` or `(recommended)` is the recommendation (the marker is not part of the option's `text`); at most one per question.
- A question is answered when exactly one option is ticked. Two ticked options are no answer, and `check` says so (hint `question-problem`), as it does for a key used twice, a question
  without options and a second recommendation.
- The key is the engine's: the number is never reused, a question written without one gets the next free number when it is answered.
- The section is prose, as `## Plan` is: a task without it is complete and valid. The engine reads, ticks and unticks; it never changes `status` or `actor` when
  the last question is answered (that is for the person).
- Write: the operation `answer` above, `answer <id> <q1|#n> <n|clear>` on the command line, `:Tasks task answer <id> [question= option=]` in the editor (without
  `question=` it asks the open questions one after the other and marks the recommended option).

**Finishing a task takes two steps** on purpose. `done_preview` (a read method, `{"id": ...}`) answers `tasks.donepreview`:
the target, the README row, the steps it would tick, the plan it would close (`closes_plan`) and the project that follows it (`closes_project`: no other plan except a parked one and no task of its own is open), the tasks it would free
(`freed`), the next round of a routine (`next_round.due`), the `etag` of the file it read and a `confirm` token for exactly that version. `done` needs the token; if the
file changed since, it is a `conflict` and nothing moves. A task that is finished already answers `unchanged`, so a
repeated request does no harm. The token is not a secret (the engine keeps no state); a host that needs authorisation
adds its own.

**What a front end may not write.** A text value with a control character (ESC and the rest of C0 but the tab, NUL, DEL, the
8-bit C1 range, the Unicode line separators) is refused: other tools print the files to a terminal and parse them. Limits are
kept on writing (title 300 characters, summary 1000, lists of 100 entries of 300 characters). A `refs` entry that is **new** must be a plain relative path, optionally with a line suffix
(`lua/a.lua:42`, `lua/a.lua:10-20`), an anchor (`docs/a.md#top`), a `repo@commit` or an id: no `..`, no drive or network
prefix, no absolute path, no control character, no colon but the line suffix. Entries the task already has stay as they
are. A task file that is a link is not written through (`forbidden`). No error carries a path of this machine, only ids.

**`move_area`** answers, as a dry run, with `move`: `new_id`, `from`, `to`, `conflicts` (the slug is taken in the target
area, or the target of an earlier `move_area` of the same request: the dry run sees the disk, and the real run makes the
moves one after the other), `references` (the `blocked_by`, `after`, `refs`, plan `target` and documents that name the
old id and would dangle) and `notes`. Without `dry_run` the move is made (see the table above); a report that is not `ok` (a taken slug)
fails with `invalid_argument` and writes nothing.

The exit code of `tasks call ops` is `0` when every operation worked, `1` when any failed (the document says which), `2`
for a bad request.

## The persistent host

`nvim --headless -u NONE -i NONE -n -l scripts/tasks-host.lua` is the same door as `tasks call`, kept open: one
process answers many questions, so the modules are loaded once and an unchanged vault is read from the parse cache.
The vault and the switches come from the environment, as for `scripts/tasks.lua`. The documents are those of
`tasks_nvim.api.call`, byte for byte (a spec holds that).

One line each way, UTF-8, fields separated by a tab, lines ended by `
`:

| Direction | Line | |
|---|---|---|
| host to client | `ready	1` | once, when the modules are loaded; the number is the version of this protocol |
| client to host | `<id>	<method>	<params>` | `<id>` is digits (at most 15); `<params>` is the JSON of the request (`ops`: the whole request; the read methods: the `params` object), empty for none; no line break in it |
| host to client | `<id>	<document>` | the document on one line, or a `tasks.error` |

One question is in flight at a time and each is answered completely before the next is read. A line that is not a
request is told on stderr and skipped. The host ends when its stdin ends (a client that dies leaves no process
behind); a request is at most 256 KiB plus its head.

## The rules every document keeps

- **No path of this machine.** A file is `<area>/ROADMAP/tasks/<slug>.md`, relative to the vault; an absolute `refs:`
  entry shows as `<external>/<name>`; the vault root inside a message is `<vault>`.
- **Missing means unknown, never 0.** A task without an effort has no `effort_days` and no `roi`; a task without a
  value has no `value`. Only values that are valid words of their enum are written.
- **A broken task is still there.** It has `valid: false` and `problems`, it does not vanish from the list. One without a
  usable status is in `unlisted`.
- **A document is at most 8 MiB.** A bigger one is the error `payload_too_large`, not a cut-off document. Ask for a page
  (`list`) or an area. (An error document is exempt: the limit must never keep a client from being told why.)
- **Canonical bytes.** Object keys are sorted by byte value; an empty list is `[]`, an empty object `{}` (as its kind says,
  never the other); a whole number below 2^53 is written without a fraction, any other number with the fewest digits that
  read back as the same number; `NaN`, `inf` and a whole number of 2^53 or more are an error, not a silent loss of
  digits. Strings are valid UTF-8 (a bad byte becomes U+FFFD); control bytes (C1 included), `"`, `\`, U+2028, U+2029 and
  `<` are escaped, so a document can sit inside a `<script>` block and be printed to a terminal as it is. There is no
  whitespace: the same vault gives the same bytes.

## `etag`, `rev`, `digest`

| | |
|---|---|
| `etag` (a task) | `sha256:` and the first 16 hex digits of the SHA-256 of the **bytes** of the task file as they were parsed. A later write compares against it; there is no second read, so no race between reading and hashing. A file that was not read has none. |
| `rev` (`snapshot`, `list`, `task`) | what the document's content stood on: `rev:` and six hex digits over the id and `etag` of the tasks in the document, of every plan file, of the meeting files (when there are some), and of the unlisted files. The same request with the same `rev` found the same files. |
| `digest` (every document that comes from a scan) | `sha256:` and 16 hex digits of the compact document **without `generated_at` and `engine`**. Two runs on an unchanged vault give the same digest, whenever and by whichever build of the engine they ran. |

## Errors

A `tasks.error` document: `code`, `message`, `retryable` and, when there is more to say, `details`.

| `code` | |
|---|---|
| `invalid_argument` | the request is not valid JSON, has an unknown field or parameter, or a value out of range |
| `not_found` | unknown method, area or task; no vault |
| `conflict` | the file is not the version the caller saw (`if_match`, `expect`, a stale `confirm`, a list that moved on); `details` says what was found |
| `exists` | the slug that was asked for is taken |
| `forbidden` | a task file that is a link is not written through |
| `unsupported_schema` | the request asks for a higher `schema` than this engine speaks (judged first: a request of a newer schema may carry fields this engine does not know, and that is version skew, not a typo) |
| `payload_too_large` | a request over 256 KiB, a document over 8 MiB, more than 100 operations, a value over the limits |
| `locked` | another writer holds the file right now, or git rewrites the vault's tree (a rebase or a pull with an autostash, a merge, a command holding `index.lock`: every writing operation waits up to 3 s for it, then refuses and writes nothing; a dry run and the reads do not wait) (`retryable: true`) |
| `lock_stuck` | a lock nobody will release (older than the takeover age and not deletable, or a folder where the lock file should be): the message names the lock to remove by hand |
| `rollback_incomplete` | a failed write could not be fully undone; the message names the files |
| `io` | something could not be listed, read or written |
| `internal` | a bug of the engine; the message says what failed |

## Writing a reader

- Read `schema` first. A document with a **higher** `schema` than you know is refused; the contract only ever **grows**
  inside a version (a field is added, none is removed or changes its meaning).
- **Ignore a field you do not know.** Treat an enum word you do not know as "unknown", not as an error.
- A field that is missing is unknown. Never read it as `0` or `""`.
- Ask `hello` once: `capabilities` says what the engine can answer, `enums` which words exist, `limits` what is kept.
- Use `etag` as the version of a task and `rev` / `digest` to see whether anything changed at all.
- Send requests to a long-running Neovim one at a time (the engine is not re-entrant: a second request that arrives while
  one is being answered is a re-entry). One process per request, as `tasks call` does, needs no care.

## The vault stays the vault

The documents are built from files anyone may have edited or synced, so the read side keeps to the vault:

- **A link is not followed.** A task file that is a symbolic link or a junction is not read (it is an invalid task with
  the finding `symlink-task`, no `etag`, no body, and it is in `unlisted`); a `ROADMAP`, `tasks`, `Backlog` or `plans`
  folder whose real path is outside the vault is not read and is reported in `incomplete`; a folder of the vault root that
  is a link is no area. A vault that itself lies below a link (`/var` on macOS) is fine: it is the links *inside* it
  that count. `tasks check` reports the first as `symlink-task` (an error).
- **A ref is no way to ask about any file.** For `--stale=refs`, a `refs:` entry that is a network or device path
  (`\\server\share\x`, `//server/share/x`, `\\?\C:\x`, `\\.\pipe\x`) is skipped: a stat on it makes Windows connect to a
  host the task's author chose. An **absolute** ref is looked up only inside the places the engine was told to look in
  (the folders that hold the repos, the nvim config, the vault, `extra_bases`), after its `..` are resolved; anywhere else
  it is "found nowhere". The documents never run `--stale=refs`; `refs` is shown as written, with absolute entries as
  `<external>/<name>`.
- A file bigger than 2 MiB, a FIFO or a directory named `x.md` is an invalid task (`unreadable`), never a stall.
