# Changelog

All notable changes to tasks.nvim. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
the version is not tagged yet (the repository is not published).

## [Unreleased]

### Added

- Contacts (`tasks_nvim.contacts`, `tasks_nvim.contact_write`, `docs/ENGINE.md` "Contacts"): one file per person, `<area>/CONTACTS/<slug>.md`, in the id namespace of the area (`vault.has_plan_or_project`, `move_area` and `check` know them: `contact-id-taken`). `tasks-export/1` (additive, capability `contacts`): the documents `tasks.contacts` and `tasks.contact` (the methods `contacts` and `contact`), the write operations `contact_new`, `contact_set` (`inverse`, `if_match`) and `contact_delete` (the `inverse` makes the contact again); `check` codes `contact-name-missing`, `contact-bad-email`, `contact-bad-phone`, `contact-bad-tz`, `contact-too-many`; the CLI `tasks contact new|set|delete|show` and `tasks contacts`. No mail address and no phone number is named in a finding, a `problems` entry, an error or a note (`contacts.scrub`); a contact lives in any area, no place is checked
- `tasks-ops/1` (additive, capability `node_result`): `node_set` takes `result`, the `**Ergebnis:**` line of the point's exercise block, written before the state so one call writes the proof and closes the point; the inverse gives the whole note back. `tasks point <id> <key> --result=<text>` does the same (`--state` becomes optional when a result is given).
- Exercise blocks under a learning point (`tasks_nvim.exercise`, `docs/ENGINE.md` "Exercise blocks"): the note of a `Üben:`/`Mini-Projekt` point carries `**Aufgabe:**`, `**Fertig, wenn:**`, `**Nachweis:**` and `**Ergebnis:**`; a point with a `Nachweis` is learned only with a result (`lernbaum.set_state` refuses, `lernbaum.set_result` and `paths.point` `result` write it), and `check` hints `path-exercise-vague` for exercise points with no task text.
- `:Tasks agent <id> kind=handoff mode=run` watches the job and offers the summary ai-desktop returns (`handoff-summary/1`): checked first (`review.handoff_summary`: schema, job, date, 4096 bytes, control characters, the four headings in order), shown as text in `tasks://summary/<id>`, and written only after a yes as the section `## Agent-Verlauf (Job <id>, <date>)` with the headings one level down, through `set_section`. A failed or cancelled run reports no summary, `summary_error` is named. Spec `tasks_handoff_summary_spec`.
- `:'<,'>Tasks new` (with an area, and the form without one) writes a `code-ref/1` block under `## Kontext` of the new task (contract `appkit/schemas/code-ref/1`): repository name, HEAD `sha` (`dirty` for unsaved or uncommitted changes), repo-relative `file`, the whole `lines` range, `lang`, the `symbol` where tree-sitter has it and an `excerpt` of at most 4 KiB cut on a whole character (`truncated`). The block is checked with a Lua port of the reference check (`tasks_nvim.code_ref.problems`, specs against the goldens copied from appkit `94a97ff` into `TESTS/golden/code-ref/`); an invalid document is never written. In a private area (`new.private_areas`, or any area of a vault folder named in `new.private_vaults`, default `tricentis-vault`) the excerpt is written only after a yes. The block stands in the file before `new.open_after` asks; `refs:` is unchanged. Spec `tasks_code_ref_spec`.
- `:Tasks open [<id>] --desktop | --web` shows a task alone in tasks-desktop (`http://127.0.0.1:<port>/#task=<id>`, port from its `hub.json`) or in tasks-web (`open.web_dir`, `tasks.html#task=<id>`); no id means the task of the buffer, else the one created last; on the workstation only `--web`. After `:'<,'>Tasks new <area>` the option `new.open_after` (`ask` default, `always`, `never`) decides whether the task opens there (new module `tasks_nvim.open_app`, `tasks_nvim.ai.hub_record_of`). Spec `tasks_open_app_spec`.
- The items of `tasks.learn_next` and `tasks.learn_notes` carry `etag`, the version of their path file (as `PathEntry.etag`), so a page writes a point with `node_set` on the version it read (`if_match`; a change in between is a `conflict`) instead of blindly.
- `snapshot.projects[]` carry `stage` (capability `requires`), the words of a path's stage: `done`, `parked`, `waiting` (an open hard requirement), `doing` (`status: doing`, or a plan or task of it finished), else `idle` (`requires.project_stage`), so a map of paths and projects needs no rule of its own.
- `requires` (capability `requires`): an id whose area only another configured vault has (`setup({ vaults })`, as a milestone's `includes` reads it, now `vault.area_of_other_vault`) is `kind: "foreign"` instead of `unknown` (no `requires-unknown` then), and a `[[slug]]` that names no or several ids is in the list as `kind: "unknown"` with its text as written (it was missing; `check` keeps saying the link problem), so the map draws a box for every entry.
- `requires` (capability `requires`): an id of another vault (`<vault>:<area>/<slug>`, `<vault>/<area>/<slug>`) and a broken entry stay in the list of the documents as `kind: "foreign"` and `kind: "bad"` (`id` as written, `met: false`, never in `waiting_on`, no gate held), so a map draws them as a box; they stay the file's fault `path-bad-requires` / `project-bad-requires` for `check`. `tasks path` prints them as `foreign` / `bad`.
- `tasks done <id> --commit [--commit-message=<text>]` commits the files the finish wrote in the vault at once (`tasks_nvim.vault_commit.snapshot`/`changed_since`: what differs afterwards from before, without the generated index files), from the staging area of `tasks commit`, so other sessions' files stay out. Without `--commit`, `done` prints a line `commit-paths` for `tasks commit`.
- `tasks learn next` filters its text output by `NVIM_MACHINE_ROLE` when `--machine` is not given, as `tasks path` does (`private` takes `wsl` points too); a first line `machine` says so, `--machine=all` shows every point, an unknown role filters nothing (`note` line), `--format=json` and the contract stay whole.
- `tasks push [<sha>...] [--attempts=n] [--dry-run] [--no-sync]` pushes your own commits of a shared vault from a throwaway worktree on `origin/main` (new module `tasks_nvim.vault_push`): conflicts in generated files are solved by rendering the index (`TASKS.md`) or keeping both sides' lines (`Backlog/README.md`, `_Telemetry/history/*.jsonl`), any other conflict names the file, a rejected push starts again (5 attempts), the pre-push hook sees only the worktree, the shared checkout is rebased afterwards with the files of other sessions kept (an autostash that conflicts in a generated file is rendered anew and dropped), and the worktree is removed with `git worktree remove`. Replaces the script `TOOLS/scripts/push-vault.sh` of the tasks-vault.
- `tasks merge-driver install|status` sets up git's merge driver `tasks-index` for the generated `ROADMAP/TASKS.md` (new module `tasks_nvim.vault_merge`; the lines for `.gitattributes` also give `Backlog/README.md` and the history series the built-in `union`). A rebase, cherry-pick, `pull --rebase --autostash` or `stash apply` no longer ends in a conflict in a generated index; the next render makes the file right, the pre-push gate (`index-stale`) stays the control.

### Fixed

- `:'<,'>Tasks new` writes the `refs:` entry of a selection relative to the git root of the file and with the whole range (`lua/a.lua:5-12`); it was relative to the working directory of the editor (a wrong path from any other folder) and named only the first line.
- `tasks push` no longer reports `pushed` for a pick that could not be committed (signing, a hook, a lock): only a pick that leaves nothing staged is skipped, any other failure is an error with git's words; the pushed list is taken before the push, and a push counts only when the head is on the remote afterwards (`nothing new landed` as a note otherwise).

- `plan_set`, `project_set` and `path_set` no longer name the file by its path on this machine when the frontmatter cannot be written (`cannot change C:/…/x.md: …`, e.g. a line holding a map the writer does not rewrite): the message is redacted like every other one of the contract.
- `:Tasks done`, `:Tasks plan-close`, `:Tasks project-close` and a finish from the dashboard (`batch.done_many` through `dash_core.apply_done`) in the editor no longer date refs with git while the editor waits: a generated block of a `chain.marker_docs` document that was written with `--stale=refs` is left as it is, and the message names it (`plan_scope.refresh_document(..., { defer_stale_refs = true })`, `done_flow` option `defer_stale_refs`). The CLI's `tasks done` renews such a block as before.
- `:Tasks attach <id> from=clipboard` no longer freezes the editor while the clipboard tool runs (`powershell.exe -STA` on Windows, 80-450 ms): the image is read through `lib.nvim.clipboard_image.save_async` and attached when it is there (`attach_source.attach_async`). A newer `from=clipboard` to the same task drops an older one still waiting, before anything of it is written (an attach to another task meanwhile drops nothing); the vault is the one of the call. With an older lib.nvim (no `save_async`) the editor waits as before. The CLI, `tasks-ops/1` and the "attach a screenshot" entries of the form and the dashboard still wait.
- A checklist is no summary: a task, plan, milestone or meeting without `summary:` whose text starts with checkbox items (`## Akzeptanz` with `- [x] it ships`, an agenda `- [ ] Blockers`) no longer shows those lines, marks and all, as its summary. `model.first_paragraph` skips checkbox items (`-`, `*`, `+`, `1.` with `[.]`) and the indented lines below them, and a checkbox item ends a paragraph of text before it; a list without boxes is still text.
- The generated overview of a project (`projects --of=<id> --write=<file>`, the block of `project-new --template=learning`, the refresh after a finish) is written in the language of its document (German or English words outside the generated blocks), else the language of the vault's marker file (`tasks-vault.json`, `lang`), else German: `Lernpfad | Status | Punkte | Offen | Fortschritt`, `Noch keine Pläne und keine Lernpfade.`, `Eigene Tasks des Projekts: n offen.` (`projects.WORDS`, `projects.lang_of`, `projects.lang_for`). An English block in a German document is stale once (`--check`) and is rewritten by the next `--write`.
- A learning path (or a task, plan, milestone or meeting) without a `summary:` whose text starts with `## Lernpunkte` no longer gets its checkbox lines as summary (`- [ ] Root {#root} - [x] First {xp=60} …` under the title in `tasks.paths`/`tasks.path` and the app): `model.first_paragraph` skips the sections `## Lernpunkte`/`## Learning points` and `## Level`/`## Levels`/`## Stufen` as the learning tree and the levels read them (a level-2 heading, up to the next heading of level 1 or 2). Such a path has an empty summary; text before or after those sections is taken as before.
- A vault given relative to the working directory (`--vault=.`, `--vault=../vault`) is made absolute once, in `vault.root`. With `.` the `link-repo-absent` hint did not apply (the folder above `.` was unknown, so the links stayed warnings), and the contract's documents named the file by its base name only, redacted every `.` of a message (`lib<vault>nvim`) and gave the vault the id `.`.
- `check` no longer warns once per link when the links of a learning path, task, plan, project or meeting lead into a neighbour repo that is not checked out on this machine (the first folder outside the vault the link names is not there at all, e.g. `../../../../Literatur/...`): one hint `link-repo-absent` per repo counts them, "repo ../Literatur is not checked out: n link(s) in m file(s) unchecked (line N: the first in this file)". A file missing in a repo that is there stays `path-link-missing` / `link-missing`. `tasks ci` gates as before, only without those warnings; `path-new --from=` no longer refuses a draft for such links (they are a hint). New `mdlinks.outside_folder`.
- `check` no longer warns `blocked-by-parked` for a task that is `parked` itself: a chain shelved on purpose (the same `waits_for`, one parked task behind the other) is no fault. An open task behind a parked one is still warned about. The plan state of such a task stays `stuck`; `next` offers neither.
- `:Tasks plan`, `:Tasks estimate` and `:Tasks quickwins` with `--stale=refs` no longer make the editor wait for git: as `:Tasks list` does, every other criterion first, the refs of what is left in the background (`staleness.compute_async`), then the scope again with the dated refs. A newer command of the same name cancels the delivery of the older one; `ui.cmd.pending_ref_checks()` counts these checks too. The CLI stays synchronous.
- A write through the door in the editor (`:Tasks meeting new|close`, `:Tasks reopen`, adding an agent's review or proposal) no longer waits for git: right before `ops.run` the editor asks git for the commit of the engine (`engine.git` in the head of every document) in the background (`contract.prewarm`); a document made while git runs says `unknown`. `setup()` starts no process. The CLI and `tasks-host` do not prewarm.
- `path_levels` writes the words of the level lines in the language they use already (`Path done`, `Reward:` stay English), else in the language of the vault's marker file (`tasks-vault.json`, `lang`), else German (`lernlevel.lang_of`, `lernlevel.WORDS`).
- A dry run of `tasks-ops/1` reserves the ids earlier operations of the request take, for `new`, `plan_new`, `project_new` and `path_new` alike: a second plan of the same title (or a task and a plan of one slug) gets `-2` in the dry run as in the real run.
- `path-link-missing` compares a link with the images and badges it leaves to their own findings by the file it names: `./assets/x.svg` or `assets/x%20y.svg` next to an image `assets/x.svg` (or `assets/x y.svg`) is no second warning. `path-image-missing` finds a percent-escaped image (`assets/x%20y.svg` names `x y.svg`).
- `tasks path` shows a level in percent as whole XP (or points), rounded up: 25 % of 505 XP is 127 XP, the point at which it is reached, not 126.25.
- A refused write on a claimed task names `--by=<owner>` first (for your own claim), `--force --note=` after it; `--help` names `--by` (and `--force --note=`) for `set`, `done`, `attach` and `folderize`.
- A link to a machine's path (`$REPOS_DIR/x.md`, `~/x.md`) is no relative link: `link-missing` and `path-link-missing` no longer call it dead, and `folderize` no longer puts a `../` before it.
- An open learning path of a project (`project:` in the path file, status other than `parked`) is open work of it: `check` no longer calls a curriculum of open paths `project-no-open-work`, and `project-close` / `project_close` refuse while such a path is open (it is named in the message and in `details.holding`), as for an open plan. A finish by `done` does not close such a project either.
- `path-link-missing` / `link-missing` fold `..` of a relative link by the text, the same on every system: on Linux a link out of a folder that is not there yet (`../tasks/x.md` of a draft whose `ROADMAP/paths/` is not made) counted as dead, on Windows it did not.
- `check` names the line of the file for the findings of a learning path's tree and levels (`path-duplicate-key`, `path-bad-mark`, `path-arrow-dangling`, `path-image-missing`, `level-*`, the lines of `xp-missing`), also the line a message points at ("already on line 10"). It named the line of the body, the frontmatter block not counted. The findings of one path are `check.path_file_findings` now.
- `folderize` and `attach` no longer break the relative links of a task, plan, project, learning path or meeting they turn into its folder form: every relative Markdown link and image (not `http(s):`/`mailto:`/`#anchor`, not `assets/`, not inside code) gains a `../`, so `../../Literatur/buch.md` still names the book one folder deeper; a failed `attach` puts the file back with its text as it was. New module `tasks_nvim.mdlinks`.
- A dry run of `tasks-ops/1` sees the plans and projects an earlier `plan_new`/`project_new` of the same request would create: `[plan_new, new{fields.plan, phase}]` (and `project_new` with `fields.project`, `set` with `plan`/`project`/`phase`, `plan_new` with `project`) answers as the real run does instead of "is no plan file". A stage the new plan does not have is still refused.

### Changed

- `tasks ci` shows the hints of `check` (severity `info`, e.g. `link-repo-absent`) as `info` lines in its log; they never count, the exit code stays the same, `--strict` included.
- `tasks index <area> --staged` checks out only the vault's top files and the area's `ROADMAP/` from the staging area instead of the whole vault (`checkout-index --all` of about 8000 files): about 1.5 s instead of 15 s in the real vault. The rows name blockers by id, so no other area is read.
- `tasks set <id> key=value` takes the id of an open learning path, plan or project as well (when no open task has it) and changes the frontmatter of that file, as `path_set` / `plan_set` / `project_set` do: `tasks set <path> project=<id> status=doing` no longer ends with "no such open task". `tasks-ops/1` (additive): `path_set` takes `tags` (a list; `on-workstation` / `not-on-workstation` go to the promoted tasks).
- An arrow in the text of a learning point is text unless an id `<area>/<slug>` follows it and nothing but `{xp=…}`, `{#…}` or the reason after that: `Test rot → grün` or `Klick → Route → Engine` is no longer `path-bad-arrow`. A `→` before a word that has the form of an id but is none (`area/Slug`) stays text and is a hint of `check` (`path-bad-arrow`, severity `info`), never a warning; the tree carries such hints in `hints` (not in the contract's `tree_problems`).
- The learning template of a path (`path-new --template=learning`) follows the rules of learning paths: the sources table has the column `Geprüft` (date or `ungeprüft`), the hints under `## Lernpunkte` name the stages `orientieren` … `festigen` and the literature group, and the sections `## Level` (a commented example) and `## Ergebnis schreiben` are new. The hints stand above the syntax line, so a tree written below them never takes a hint into a subtree.
- A slug made of a title (`new`, `plan-new`, `project-new`, `path-new`, meetings, the key of a promoted point) is cut at a word boundary of the title: whole words as long as they fit, a hyphenated word like `Web-Variante` counts as one. Before, it was cut after 60 characters, inside a word (`…-und-webvari`).
- `tasks index <area> --staged` says when the working tree keeps an index file that is not the staged one (`tree_differs` on the result): `check` reads the tree and calls it `index-stale` although the commit holds the right one, which read as "`--staged` did nothing" in a linked worktree of the vault. Covered in a linked worktree; its staging area is the one written, the main checkout's stays untouched.
- `reminders.on_start` is opt-in now: the one line at startup about due reminders no longer shows unless `setup({ reminders = { on_start = true } })` asks for it.

### Added

- `tasks check --sources --fix` takes a target on another host only with `--allow-host-change` (hosts compared without `www.`, port, user info and case); otherwise the link is `kept` with the reason `other host, check by hand`. A domain that changed hands can redirect anywhere, so a person reads the `fixed old -> new` lines first. Same host with another path, `http` to `https` and a `www.` change stay automatic.
- `tasks path-new --from=<draft> [--dry-run]` reports the hint `table-ragged` (with the draft's line) for a row of a table in `## Notiz im Detail` that has more cells than its header: a pipe in code (`ls -l | less`) splits a cell in Markdown unless it is written `\|`. A hint, so it never refuses the draft; tables in code fences and in other sections are left alone.
- `tasks check --sources --fix`: a link of the `## Quellen` table that moved for good (301 or 308, a chain to its end) is rewritten to its target (`fixed` lines); a temporary redirect, a front page, a step back to http and a target that would break a Markdown link stay (`kept` lines with the reason). Only the address changes in the row; with `--write` the same write fills `Geprüft`. Never without the flag.
- `tasks path <id>` filters the text output by `NVIM_MACHINE_ROLE` when `--machine` is not given (`private` also shows `wsl` points); `--machine=all` shows every point, `--format=json` and `--schedule` stay whole, and an unknown role filters nothing and prints a `note` line. The `machine` line says `from NVIM_MACHINE_ROLE`.
- `tasks paths --format=json`, the path entry of `tasks.paths` / `tasks.path` and the rows of a project say how many leaves are `{safety}` (`safety`) and how many are for each machine (`machines`, by the effective `{machine=…}`), only when there are some (capability `path_marks`); the TSV of `tasks paths` keeps its columns. Schema, types, golden and `docs/CONTRACT.md` follow.
- `tasks.paths` with `levels: true` (capability `paths_levels`): every level of every path in one request, as `tasks.path` has them, plus the XP or percent missing to a level not reached and, from the series of the learning figures, the day each level was reached and each reward granted. For the badges, rewards and overview of the desktop app.
- A series of the learning figures: one row per day and learning path in `_Telemetry/history/learn-YYYY-MM.jsonl` (learned, seen, dropped, open, total, XP, hours done, level, levels reached and rewards granted), written by `history record`, `index` and the operation `history_record` (`learn_rows`, `learn_file`) when a path changed (`tasks_nvim.learn_history`). `tasks.learn_history` (capability `learn_history`) and `tasks learn history [<area>] [--since] [--until] [--step=day|week|month]`: per step what was learned, the learning days and the streak, per path the day each level was reached and each reward granted, the pace of the last four weeks and the weeks left at that pace; no step before the first day of the series. `tasks.learn_next` orders the paths by their last active day from it. For the overview, the statistics, the badges and the time view of the desktop app.
- `tasks.learn_evidence` (capability `learn_evidence`) and `tasks learn evidence [<area>] [--competence=<id>] [--done]`: the evidence of all learning paths (points whose label starts with `Nachweis:`, `Aufgabe:` or `Ergebnis:`) with state, link, path and its competences; `{for=t4}` / `{for=p3.5}` on a point names the stage it proves (`lernbaum`, written back as it was; a bad one is `path-bad-for`). For the view "Nachweise" of the desktop app.
- Competences in the vault: one file per field of knowledge in `<area>/ROADMAP/competences/<slug>.md` (`title`, `group`, `t`/`p` stage in theory and practice 0..8 in halves or `?`, `target_12`/`target_24` a stage or `{t: N, p: N}`, `assessed`), a learning path names its field with `competence:` and its aim with `competence_target:` (`tasks_nvim.competences`). `tasks.competences` (capability `competences`) and `tasks competences [<area>]` list them with the paths that name them and the scale (0 Unbekannt … 8 Mastermind) in the language of the vault; path entries carry `competence` and `competence_target`, `path_set` writes both; `check` reports broken competence files and `competence-unknown`.
- `tasks.learn_notes` (capability `learn_notes`) and `tasks learn notes [<text>] [--kind=note|link|image] [--area=…] [--paths=…] [--done] [--limit=N]`: the notes, links and images of the learning points of all paths in one request, with path, stage and state, searched without case over label, note and link; `include_done` adds the finished paths. For the view "Notizen & Quellen" of the desktop app.
- The hours of a learning path in the contract (capability `path_hours`): `hours { planned_min, planned_max, done, open_min, open_max }` on a path entry of `tasks.paths` and `tasks.path` when a point carries `{h=…}` or `{done_h=…}`, and `schedule` in `tasks.path`, the sessions of `## Zeitplan` each with its hours, result and state (`learn.hours`). For the view "Lernzeit" of the desktop app.
- `tasks.learn_next` (capability `learn_next`) and `tasks learn next [<area>] [--machine=…] [--n=N] [--paths=…]`: for every running learning path (stage `doing`, or `idle` with its project begun) the first points that may be learned now, in document order: open, not blocked, not optional, on the machine; each with its stage, link, planned hours, XP, `safety` and machines (`tasks_nvim.learn`, `tasks_nvim.contract_learn`). For the view "Nächster Lernschritt" of the desktop app.
- `tasks check --sources [<file|dir>] [--write] [--timeout=<s>]` asks the web links of the `## Quellen` table of a learning path (HEAD with a time limit, GET as fallback) and tells dead (404/410), blocked (401/403/429: not checkable, no error), moved and unanswered links apart; exit 1 on a dead link. `--write` puts date and answer into the column `Geprüft`. It makes requests only on this flag, never in `check`, `ci` or the vault hook (`tasks_nvim.sources`).
- Learning paths and projects build on each other: `requires: [id, ...]` and `requires_gate: soft|hard` in the file of a path or project (`tasks_nvim.requires`). A requirement is met once that path or project is finished. The soft gate (the default) only says so (the item keeps its stage; a note when it is finished anyway); the hard gate keeps the path from being finished (`path_close`) and its line of the whole path in `## Level` open, and a project from being finished (`project-close`, `project_close`, the close a finish takes with it); a hard requirement of a project holds for its paths too. Work may begin at any time. `path-new` and `project-new` take `--requires=<id,id>` and `--requires-gate=soft|hard`, `tasks set <id> "requires=[a/b,c/d]"` changes it (known ids only, no circle). `check` reports `requires-unknown` and `requires-cycle`, a broken entry `path-bad-requires` / `project-bad-requires` (and `...-bad-requires-gate`), a plan with the field `plan-requires`. `tasks path` shows each requirement and the gate, `tasks paths`, `tasks projects` and the generated overview of a project say `waits for <id>`. Contract (additive, capability `requires`): `tasks.paths`, `tasks.path` and the projects of the snapshot carry `requires` (`{ id, gate, kind, met }`), `requires_gate` and `waiting_on` (`{ id, via? }`, the open hard ones); path entries carry `stage`; `tasks.paths` takes `include_done` (the finished paths too, and `done_projects`) and answers `requires_cycles`; `path_new`/`project_new` take `requires` and `requires_gate`, `path_set`/`project_set` take them in the patch; a waiting `path_close` / `project_close` is refused with `details.waiting_on`, a soft one answers a note.

- `:Tasks milestones [<area>]` shows the milestones in a float (status, due, members done of all, overdue), and `:Tasks done` names a milestone the finish reached (`milestone reached: <id>`) or set back to `doing`.
- `tasks commit <path>... --message=<text> [--dry-run]` commits only the paths you name in a shared vault, from a staging area of its own (new module `tasks_nvim.vault_commit`): another session's staged files stay staged and out, and the `TASKS.md` and Backlog README of the touched areas are generated from the commit itself, not from every session's tree. `HEAD` moves by compare-and-swap, so a commit of another session in the meantime is kept (the commit is built again on top). ### Fixed

- `done` no longer finishes the old text of a task while git rewrites the vault (another session's pull with `--rebase --autostash`, a merge, a command holding `index.lock`; also in a worktree): it waits up to 3 s for git and otherwise refuses with `git is rewriting the vault (...)`, `locked` and retryable in the contract (a left-over `index.lock` is named as one). When git starts during the finish and the open file comes back, the result carries `came_back` and the finish says so in its notes instead of leaving one task in two places without a word (`tasks check` shows it as `duplicate-id`). New module `tasks_nvim.gitbusy`.
- A promoted task that goes to `blocked` or back, or is reopened, takes its learning point along as `done` does: `set status=blocked` writes `[!]`, a `set` out of `blocked` and `reopen` write `[ ]` (the reason dropped). The `set` and `reopen` operations of `tasks-ops/1` name the container in `changed_ids`. `promote-state-drift` now also reports `[!]` against an open task and `[ ]` against a blocked one.
- Every writing operation of `tasks-ops/1` (`set`, `reopen`, `promote`, `node_set`, `path_*`, `meeting_*`, `claim`, ...) waits for git like `done` does: while a rebase, an autostash, a merge or `index.lock` rewrites the vault it waits up to 3 s and otherwise answers `locked` (retryable) and writes nothing, so a change no longer collides with the autostash coming back. One check at the door of the operations; a dry run and the reads do not wait.
- `index <area> --staged` names the files of the area it counted besides `HEAD` (`staged<TAB><path>`, with a note how to unstage one): a `git pull --rebase --autostash` whose stash hits a conflict leaves the rest of the tree staged, another session's claim among it, and the index then listed that task as `doing` without a word. A staging area with a conflict in a task file is refused now (`checkout-index` skipped such a file, so the task dropped out of the index); a conflict in the generated index alone is resolved by the run.
- `:Tasks done <id> remind=+7d` keeps the reminder: the editor handed only `done_in`, `commits` and `date` to the finish and dropped `remind=` (and would have dropped the new `outcome=` / `reason=`).
- `:Tasks new --draft` and `:Tasks agent`: `agent.confirm_run` and `agent.drop_job` prove the ai-desktop of the hand-over again (`GET /health` with its instance) before the control secret goes out, as `agent.hand_over` does; they take the proved peer of the hand-over (`result.peer`) instead of a port from a `hub.json` read again after it. ### Changed

- The specs run on testing.nvim (`.testing.lua`, `scripts/test.sh`, CI); `TESTS/run.lua` is gone, the specs and `TESTS/harness.lua` are unchanged. All testing.nvim guards (fs, state, scheduled errors, prompts, deprecations, processes) fail the run; only `nvim`, `git` and (for the `scripts/test.sh` spec) `bash` may be started.
- `done` is split into plan, execute and rollback (same behaviour and messages); `staleness.compute` into resolve,
  date and compare.

  `--stale=<days>`); a failing refs check keeps the tasks that carry refs and marks them `unverified`.
- `fsio.read` refuses anything but a regular file of at most 2 MiB.

### Security

- The read side stays inside the vault: a task file that is a symbolic link or a junction is not read (`symlink-task`);
  a `ROADMAP`, `tasks`, `Backlog` or `plans` folder whose real path leaves the vault is not scanned and is reported; a
  folder of the vault root that is a link is no area.
- `--stale=refs`: a `refs:` entry that is a network or device path (`\\server\share`, `//server/share`, `\\?\C:`) is skipped instead of being
  stat'ed (on Windows that connects to a host the task's author chose), and an absolute ref is looked up only inside the
  places the engine was told to look in.
